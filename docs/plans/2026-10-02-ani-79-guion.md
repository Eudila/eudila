# ANI-79 · Guion del prototipo comercial

**Objetivo:** entregar un recorrido de seis pantallas para ANI-80, con indicadores, mapa, corte territorial y datos simulados definidos, distinguiendo el código disponible de la propuesta institucional.

**Arquitectura:** un único documento Markdown en `docs/content/prototipo-comercial.md`, con texto del presentador, contenido y acción por pantalla, tablas de datos reproducibles y límites de la conversación. Se enlaza desde README. Este issue entrega el guion; ANI-80 construye las pantallas.

**Herramientas:** Markdown, Git y Python estándar para contrastar las sumas de las tablas. Sin nuevas dependencias ni cambios de comportamiento.

## Decisiones

- Se consideran cinco pantallas compactas o seis con un paso separado para el detalle territorial. Se eligen seis para explicar el denominador y los límites antes de hablar de una futura implementación, dentro de 85 segundos orientativos.
- El dashboard viejo y `frontent-2/data/salta-zonas.js` orientan la composición de mapa, tendencias y detalle. El archivo correcto está dentro de `frontent-2/`. El mock contiene seis estados, índices de riesgo, dispositivos y datos demográficos; el guion usa los siete estados actuales y el alcance vigente de Eudila.
- Escenario hipotético en Salta Capital, como requiere ANI-80: zonas esquemáticas ficticias, un período fijo y tablas consistentes. No se copian barrios, poblaciones, coordenadas, índices ni assets institucionales del mock.
- La app actual permite tipo, ánimo, borrador y ayuda; aún faltan catálogo clínico, guardado e historial. El servicio institucional se propone como una maqueta sin flujo de datos desde la app, todavía por construir. ANI-80 la construirá en Figma o HTML estático externo al repo de producto, según su alcance explícito.

## Ejecución

1. Revisar ANI-79, alcance del proyecto, README, rutas reales y las referencias anteriores. Crear worktree externo desde `origin/main`.
2. Escribir las seis pantallas con pregunta, visual, acción, texto hablado y salida; identificar lo real y lo simulado en cada una. Definir el conjunto de datos, el mapa y las reglas de lectura.
3. Comprobar que semanas, zonas y escala tienen los mismos totales, que los porcentajes tienen denominador explícito y que las rutas/enlaces existen. Revisar todas las afirmaciones sobre funciones actuales contra el código.
4. Solicitar revisión independiente de los requisitos y coherencia de datos. Resolver hallazgos, publicar en `main`, contrastar SHA remoto y cerrar ANI-79 con enlaces y evidencia.
